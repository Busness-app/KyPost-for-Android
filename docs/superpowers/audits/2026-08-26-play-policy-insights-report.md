### User Data

#### In-app device removal exists and performs a real server-side delete rather than a local clear, but the app never creates an account on any developer-controlled service, so the Play Console account-deletion URL requirement needs a deliberate answer rather than a default one.
- **Policy**: **Account Deletion Requirement**
- **Severity**: 🔵 Suggestion
- **Files**: [DeregisterClient.kt](file://app/src/main/java/org/kysecurity/mail/push/DeregisterClient.kt), [PushRepository.kt](file://app/src/main/java/org/kysecurity/mail/push/PushRepository.kt), [strings.xml](file://app/src/main/res/values/strings.xml)
- **Evidence**: Discoverable in-app control: strings.xml:217 'Unpair device' with a confirmation at strings.xml:218-219 stating it 'removes the device from your account's paired devices on the server and clears its local pairing.' It is not the partial-deletion trap the policy warns about: DeregisterClient.deregister() (DeregisterClient.kt:44) issues a network deregistration and PushRepository.unpairDevice (PushRepository.kt:276) reports residue that survived the purge. The user's mail account itself lives on a server the user operates, which this app neither creates nor owns.

**Critic Verification**: Automatically verified (bypassed critic review). (Confidence: High)
- **Recommendation**: Decide explicitly what the Play Console account-deletion URL should point to, given there is no developer-held account to delete. A short public page explaining that KyPost accounts exist only on the user's own server, that in-app Unpair removes the device record from it, and how to delete the server-side account, satisfies the requirement honestly. Confirm separately whether the push relay retains any per-device token after deregistration and say so on that page.
- **References**:
  - https://support.google.com/googleplay/android-developer/answer/10144311#account_deletion
  - https://support.google.com/googleplay/android-developer/answer/13327111

### Play Console Requirements

#### The app is entirely non-functional until it is paired by QR code to a KyPost server the reviewer does not have, so a Play reviewer cannot exercise any feature. This is a stronger access gate than a password login, and it is the most likely cause of a review rejection.
- **Policy**: **Login credentials**
- **Severity**: 🟡 Important
- **Files**: [PushPairingActivity.kt](file://app/src/main/java/org/kysecurity/mail/push/PushPairingActivity.kt), [PushSyncCoordinator.kt](file://app/src/main/java/org/kysecurity/mail/push/PushSyncCoordinator.kt), [strings.xml](file://app/src/main/res/values/strings.xml)
- **Evidence**: There is no username/password screen anywhere; the gate is device pairing. app/src/main/res/values/strings.xml:11 'Not paired yet. Pair this device before using Relay mode.' and strings.xml:373 'Not paired yet. Pair this device via the Pairing menu first.' show functional workflows refusing to operate unpaired. Pairing is driven by PushPairingActivity, which consumes a kypost://native-pair QR minted by a running KyPost server (PushSyncCoordinator.attemptPairing). Because the server is self-hosted, no credential the developer can type into Play Console is sufficient on its own.

**Critic Verification**: Confirmed verbatim. strings.xml:11 reads 'Not paired yet. Pair this device before using Relay mode.' and strings.xml:373 reads 'Not paired yet. Pair this device via the Pairing menu first.' — two distinct functional surfaces refusing to operate without pairing. A search of PushPairingActivity found no password, signIn or login construct, confirming the worker's characterisation that the gate is device pairing rather than a credential form. This satisfies the Hidden Gatekeepers heuristic: the workflow requires authentication even though no login screen exists. The severity is right, and if anything the practical risk is understated, because the usual remedy of supplying a demo username and password in Play Console cannot unblock a reviewer here — pairing requires a reachable KyPost server emitting a kypost://native-pair QR. (Confidence: High)
- **Recommendation**: Before submitting, stand up a reviewer-accessible KyPost server and supply, in Play Console's App access section, both a reachable pairing QR (or the kypost://native-pair URI) and step-by-step instructions for using it. A demo username/password field alone will not let a reviewer in. Also record in Play Console that the app requires an external self-hosted server, so a reviewer who cannot pair does not read it as a broken app.
- **References**:
  - https://support.google.com/googleplay/android-developer/answer/15748846
